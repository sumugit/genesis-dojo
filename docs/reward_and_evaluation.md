# 報酬設計とループの評価観点

自動ループ（日本語の指示 → LLMが報酬を書く → 学習 → 録画 → 数値判定とVLM評価 → 修正）で、**報酬をどう設計させ、何を基準に良し悪しを判断しているか**をまとめる。
仕組みの全体像は [../README.md](../README.md)、各ファイルの役割は [../pai_loop/README.md](../pai_loop/README.md) と
[../scripts/README.md](../scripts/README.md) を参照。

## 1. 報酬設計

### 1.1 誰が、どう設計するか

- **LLMが報酬モジュール（Python）を書く。** 人は書かない（`pai_loop/rewards/sit.py` は比較用の手書き版）。
- 依頼文（`pai_loop/prompts.py`）には、日本語の指示、環境の説明（ロボット・制御周期・実測の高さ・関節順・`TaskState` のソース）、
  報酬モジュールの仕様、**人が承認した数値の成功基準（YAML）** を入れる。2周目以降は、前回の報酬コード・学習終盤の各項の平均・エラー・
  **満たせなかった成功基準（実測値つき）**・動画評価・過去の修正指示も渡す。
- 環境の説明はコード（`TaskState` など）を `inspect` で埋め込むため、コードを変えるとプロンプトも追従する。

### 1.2 報酬モジュールの契約と、LLMに伝えている設計指針

契約（[pai_loop/rewards/README.md](../pai_loop/rewards/README.md)）: `PARAMS`（数値はすべてここ）、`compute(s, p)`（重み付き済みの項の dict、各項は形 `(N,)`）、
`failed(s, p)`（形 `(N,)` の bool。Trueなら打ち切ってリセット）。

仕様文に書いている設計上の指針:

| 指針 | 理由 |
|---|---|
| 数値（目標・重み・終了条件の閾値）は `PARAMS` に置く | 設定ファイルに書き出して再現できるようにする |
| 目標から遠い初期状態でも勾配が消えないよう、指数型だけでなく**線形の項**も検討する | 立った状態から始まるため、指数型だけだと目標が遠くて学習信号が消える（手書き版 `sit.py` のコメントに書かれた設計意図。指数型だけの場合との比較実験はしていない）。 |
| 正の報酬は「生きているだけで得」になるので、失敗時の打ち切りと組み合わせる | 何もしないことが最適にならないようにする |
| `asin` / `sqrt` の入力は `clamp` する。import してよいのは `torch` / `math` / `pai_loop.task_env` のみ | NaNを避け、環境側への依存を限定する |
| 環境は全項の合計に `dt` を掛けて報酬にする。項名は短い英語 | 学習ログの `Mean episode rew_<項名>` で、どの項が効いたか追えるようにする |
| 成功基準（承認済み・変更不可）を満たす動作を学習させる。基準そのものは変えられない | 報酬を書く側が基準を緩める余地をなくす |

### 1.3 生成後の検証（`pai_loop/reward_check.py`）

GPUを使う前に、**ダミーの状態**で次を確認する。違反はエラー文としてLLMに返し、書き直させる（最大 `--gen-retries` 回）。

- `PARAMS` / `compute` / `failed` が存在する
- `compute` が空でない dict を返し、各項が形 `(N,)` の有限なテンソルである
- `failed` が形 `(N,)` の bool テンソルを返す
- `PARAMS` の float が有限である

**これは形式チェックだけで、「お座りに見えるか」といった挙動の正しさは検証しない。** 挙動は学習・録画・数値判定・評価で初めて分かる。

## 2. ループの評価観点（4層）

| 層 | 何を見るか | 出どころ |
|---|---|---|
| ① 学習中の内部値 | 平均報酬と、各報酬項の1秒あたりの平均 | rsl_rl のログ。次の依頼に「どの項が効いたか」として渡す。 |
| ② 客観指標 | 録画6秒の姿勢・高さ・足・水平移動・**ヨー（旋回）**・**足の左右差**・関節速度。0.1秒刻みの時系列と、エピソード全体の値 | `scripts/record.py` → `pai_loop/metrics.py`。**芸に依存しない量だけ**。 |
| ③ 数値の成功判定 | 人が承認し凍結した成功条件（YAML）を、②の時系列に機械的に当てはめる。基準ごとに合否・実測値・余裕を出す | `pai_loop/success.py`、`configs/tasks/*.success.yaml` |
| ④ VLM評価（盲検） | 6フレームと②の指標だけを見て、JSON（`score` 0〜10 / `success` / `observations` / `problems` / `next_fix`）で採点する。**報酬コード・報酬項・③の結果は見えない** | Claude（`claude -p`）。`pai_loop/prompts.py` の `EVAL_SYSTEM`。 |

### 2.1 成功条件（③）の考え方

- **学習の前に人が決めて承認し（`approved: true`）、ループ中は変えない。** ループは未承認の条件では起動せず、実行中にファイルが変わると中止する（ハッシュで検査）。
  結果を見てから基準を緩める余地（書き手の都合・評価役の甘さ）をなくすため。
- 形式は宣言的なYAML。指標名は固定のカタログから選び、範囲（`between` / `min` / `max` / `equals`）と、系列の指標では**合格率（`min_fraction`）**を書く。コードは書かせない。
- 指標の種類: 系列（`nose_up_deg`、`height_m`、`foot_z_max_m`、`yaw_rate_deg_s` など）、窓内の集計（`<系列>_mean` / `_max` / `_min`、`yaw_rate_steady_fraction`）、
  エピソード全体の値（`xy_max_dist_m`、`xy_path_length_m`、`yaw_total_deg`、`early_terminations`）。一覧は `pai_loop/success.py`。
- 録画のうち `window_s` の時間帯だけで判定する（立ち上がりを除くため）。

### 2.2 ③と④の統合

| ③数値 | ④VLM（8点以上かつ `success`） | 動作 |
|---|---|---|
| 合格 | 合格 | **成功として停止** |
| 合格 | 不合格 | 継続。VLMの指摘を次の依頼に渡す。「条件の抜け」の疑いとして `disagreement` に記録し、実行の最後に表示（**条件は自動で変えない**）。 |
| 不合格 | 合格 | 継続（数値が優先）。同じく `disagreement` に記録。 |
| 不合格 | 不合格 | 継続 |

- その他の停止条件（`stop_reason`）: `max_loops`（既定3）／ `time_budget`（既定3600秒）／ `llm_quota`（利用枠の上限）。
- 失敗したループは、VLMの `next_fix`・満たせなかった数値基準・エラー・前回の報酬コード・各項の平均を次の依頼に引き継ぐ。
  生成・学習・録画のどこかで失敗しても、`error` を記録して次のループへ進む。
- 評価役には「画像だけでは頭と尻の向きを取り違えやすいので、**数値（`nose_up_deg`）を優先**する」と指示している。
- 採点用のフレームは0、0.5、1、2、4秒と終端の6枚。カメラはロボットの**位置だけを追従し、向きは世界座標に固定**（初期状態ではロボットの右側面を真横から見る）。回る芸では見える面が変わるので、プロンプトで `yaw_deg` と合わせて向きを判断するよう伝えている。

### 2.3 ヨー（旋回）の指標の定義

- ヨーは、胴体の前向き軸（+x）を水平面に投影した方位。開始時を0として巻き戻し処理（unwrap）し、**反時計回り（上から見て）が正**。
- **機体が垂直に近い（前向き軸が鉛直から20°以内、つまりピッチが約70°を超える）間は定義できない。** その間はヨーを据え置き、`heading_valid_fraction` に定義できた割合を残す。
  「後ろ足で立つ」ではヨーは使えない（別の指標が要る）。
- `xy_max_dist_m`（開始位置からの**最大**距離）を追加した。従来の `xy_drift_m` は開始と終了の直線距離なので、**円を描いて戻ってくると小さくなり、「その場で回る」と区別できない**。

## 3. 新しい芸を始めるとき

1. `configs/tasks/<芸>.success.yaml` を作る（`approved: false`）。Web UI では、AI が草案を作り、画面で直せる。指標の一覧は `pai_loop/success.py` の `catalog_text()` と上の2.1。
2. 既存の録画があれば `python scripts/check_success.py <実験名> --spec configs/tasks/<芸>.success.yaml --allow-unapproved` で、基準が狙いどおりに合否を分けるか確かめる。
3. **人が内容を確認して承認する。** ファイルの `approved: true` への変更でも、Web UI の承認ダイアログでもよい。ループを動かすAIは、`approved` を変えない。
4. `python scripts/loop.py --exp <実験名> --instruction "<日本語>" --success-spec configs/tasks/<芸>.success.yaml`
